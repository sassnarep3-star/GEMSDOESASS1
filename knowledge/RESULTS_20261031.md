# Session 2026-10-31 — results: H-KDAM lane

**Question answered:** why did `gemsdoe32-h33-h33-2-b2-…-zeros.tif` score 0.2778, and can a *new* file beat it?
**Short answer:** it scored 0.2778 because it is the 0.2600 family field with the dots that sit within 2 px of
the known catalogue deleted — and known-catalogue pixels are excluded from scoring, so those dots were pure
false-positive mass. Copying or re-pruning it cannot beat it. This session built a different field
(H-KDAM) that is measurably better on the shared holdout instrument, and shipped it as a unique file.

Every number below carries its label: **HOLDOUT-DTI** (evaluator `GEMSASS1-HR-v2-segment`, 60,988 withheld
positives, 95 % CI from a 50 px tile bootstrap), **REGISTRY-MEASURED** (computed from restored bytes), or
**OWNER-REPORT** (a number quoted by a sibling site, no organizer receipt). No projection is written as a score.

## 1. Why 0.2778 (re-derived from bytes and from the official metric text)

| Step | Measurement | Label |
|---|---|---|
| Official metric | `DTI(α,β) = TP_w/(TP_w + α·FP_w + β·FN_w + ε)`, **α = 0.2, β = 0.8**, triangular kernel `(1−d/R)₊`, R = 300 m = 3 px; soft probabilities allowed | ORGANIZER-PUBLISHED ([page 967](https://www.drivendata.org/competitions/306/competition-doe-gems/page/967/)) |
| Known faults masked | "Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation" (DrivenData staff, 16 Sep 2026) | ORGANIZER-PUBLISHED ([forum 11516](https://community.drivendata.org/t/scoring-clarification-are-known-usgs-ingenious-faults-masked-when-scoring-and-are-they-in-the-final-round-label-set/11516)) |
| GEMSDOE31 → GEMSDOE32 | symmetric difference **2,545** dots on a 40,199-dot base: GEMSDOE32 = GEMSDOE31 minus the dots within 2 px of the catalogue (0.2708 → 0.2778 OWNER-REPORT) | REGISTRY-MEASURED (`evidence/kdam/nine_site_matrix_20261031.json`) |
| GEMSDOE25 = GEMSDOE30 | symmetric difference **0** — the two "different" sites published the identical 44,090-dot field (0.2600 both) | REGISTRY-MEASURED |
| Whole family | every one of the nine best files has ≥ 97.6 % of its dots within 3 px of GEMSDOE24's dots; max overlap-to-another-site = 1.000 for six of nine | REGISTRY-MEASURED |
| Implied live arithmetic | removing 6,436 near-catalogue dots and moving 0.2600 → 0.2778 implies ≈5.2×10³ weighted truth pixels of credit under the official formula | derived, OWNER-REPORT inputs |

So: the 0.2778 file contains **no new information** about where faults are. Its gain is a pruning
artifact of the masked-catalogue rule. Any file built from that field is capped by that field.

The physical mechanism of #1: in hydrothermal damage zones potassium is mobile and thorium is immobile, so
`K/Th` drops along the fracture halo (IAEA-TECDOC-1363, 2003); a magnetic contact/lineament marks the
basement structure beneath the same trace (tilt derivative: Miller & Singh 1994, doi
10.1016/0926-9851(94)90022-1; theta map: Wijns et al. 2005; analytic signal: Roest et al. 1992). A
concealed fault can show both while showing no lidar scarp — the class missing from the USGS/INGENIOUS map.
Named non-fault mimic: a lithological contact with a potassium-poor unit (no halo reversal across strike),
and pluvial shoreline benches (no magnetic expression).

**The instrument caveat, stated before the comparison was made.** The holdout rewards dots that hug the
visible catalogue (the 0.2778 live file, whose whole gain was moving *away* from the catalogue, scores
0.0044 here). The holdout and the live board are not rank-correlated (Spearman −0.08 over 17 rasters,
previous session). Therefore: A_unpruned is a *field-quality* measurement, not a live forecast, and the
shipped file is emitted at the live-calibrated rule (prune 2 px), not at the holdout-optimal one.

## 7. Irregularities flagged for review

1. **The holdout inverts the live prune effect.** The 0.2778 file scores 0.0044 here; the same field
   unpruned (0.2600 live) scores 0.1011. Any future decision that selects on this holdout will move the
   file in the direction that *lost* live score. This is why the shipped emission follows the live
   evidence, not the holdout.
2. **Eligibility is unresolved and blocking.** The rules limit competitors to U.S. citizens/permanent
   residents or U.S.-incorporated entities (previous sessions; the rules PDF was not reachable from this
   sandbox). Confirm with the organizer before uploading. This session did not upload anything.
3. **`labels.tif` is byte-identical to `existing_faults.tif`** (previous session). The local "truth" is the
   visible catalogue, so every holdout number in this repo is a catalogue-only proxy.
4. **Only nine focus sites are in the novelty registry.** Submissions published by the sibling sites named
   in the prompt (GEMSDOE44–92, WBG/KANLER/GINNY/karage/apart lanes) are outside the pinned registry and
   were **not** compared. That is a real, stated limitation of the "unique" claim.
5. **The 0.2778/0.2600/0.2708 numbers are OWNER-REPORT.** The public board this session (2026-10-31
   snapshot) shows #1 = 0.4544; no receipt ties any GEMSDOE file to a specific rank.
6. **The 52 bounded rasters** are cleared by an upper bound computed from a 7×7 window test, not by the
   exact disk overlap. The bound is conservative (window ⊇ disk) and recorded per raster.
7. **Fixture exemptions are now measured, not asserted.** The scan clears only the 482 competitive rasters and
   originally *skipped* the 7 fixtures. `scripts/audit_fixtures.py` now measures all 7 with the same shared
   `dot_overlap` and merges the numbers into the receipt (`max_overlap3_all_rasters`, `exempt_fixtures`,
   `fixture_audit`), so "unique" is backed by 489 measurements, not 482. The lattice is the only overlap above
   the 70 % limit, and it is disclosed.
8. **A first scan exempted fixtures by filename substring** (`lattice`, `calibration`), which wrongly skipped
   six competitive files such as `24gems-interior-offlattice-…` and `gems25-…-latticegap-…`. The rule is now
   directory-based (`inputs/calibration/`) plus one explicit filename, and the scan was re-run: same verdict,
   430 exact + 52 bounded.
9. **Shared-tool fixes reported once:** `scripts/fetch_registry_current.py` was rewritten to use git sparse
   checkout because the GitHub contents API exhausted its 5,000/h quota mid-run (it is idempotent and
   SHA-256 verifies every byte); `scripts/novelty_scan.py` was rewritten to scan every raster with an upper
   bound instead of skipping low-signal ones.

10. **A concurrent lane rewrote a frozen evidence file.** Commit `1acd152` (H-STEP-OVER) changed
    `registry/focus_inventory.json` from `failed: 0, complete_within_scope: true` to `failed: 114,
    complete_within_scope: false` while leaving `snapshot_utc` at 2026-10-27 and changing no data. That is a
    false regression in the audit trail; the file is restored to its 2026-10-27 bytes here and the reason is
    pinned in `evidence/release_checks.json` (`post_review_2026-10-31_implementation_sha256`).
11. **One published file is not named by any card.** The sparse placeholder
    `docs/downloads/gemsdoesass1-unique-sparse-18000dots-20261031T050135Z-8b99942e-zeros.tif` is named
    `…-8b99942e.tif` (no `-zeros`) in its own run card. The bytes are hash-locked, so
    `scripts/verify_release.py` accepts it, but the name mismatch is recorded rather than fixed silently.
