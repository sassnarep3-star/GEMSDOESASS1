2 · Verify the hash

Confirm the file before you upload

  1. Run sha256sum <file> (or the equivalent on your OS) on the downloaded TIF.
  2. Compare against the validator receipt: docs/downloads/gemsdoesass1-unique-sparse-18000dots-20261031T050135Z-8b99942e-zeros.checks.json (sparse) or the stepover checks JSON beside its TIF.
  3. Only proceed if the hash matches and all_checks_passed is true.

3 · Confirm eligibility

Official rules §1.3

The official rules limit competitors to U.S. citizens or permanent residents, or U.S.-incorporated entities. The user’s listed location is Singapore. Confirm with the administrator before any upload. No competition upload is automated from this workspace.

4 · Run the organizer uniqueness check

Before spending a slot

Run the organizer’s uniqueness check vs the full registry (the literal 70⁡/3⁡px lattice gate caps any dotted file at 22,163 dots). The full 414-raster registry is not present in this checkout and the GitHub API was rate-limited, so this check could not be re-certified here.

5 · Submit on DrivenData

Form, exact name, note

  1. Open the DrivenData GEMS Prize submission page (login required; not reachable from this sandbox).
  2. Upload the TIF (or ZIP) whose hash you verified.
  3. Use the exact submission file name and note (at most 140 characters) from the run card — do not rename.
  4. Save the organizer receipt (submission id, file hash, returned score). A score becomes ORGANIZER-CONFIRMED only from that receipt.
  5. Check the weekly submission cap (three) before spending a slot; this workspace has used 0.

Why earlier files were rejected

The “range [0, 1]” error

The portal error “Predicted values must be in range [0, 1]” is produced by NaN or out-of-range values — historically the “-nan” variants written by sibling sites. The generated sparse TIF uses explicit zeros everywhere outside the footprint and has no NaN on the whole grid, so it cannot trigger that error. Validator output: checks.json →
